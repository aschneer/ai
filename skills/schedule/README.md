# Schedule

A text-native alternative to Microsoft Project's Auto Schedule. You describe a project as plain YAML — tasks, durations, dependencies, milestones — and the tool computes every date for you using the Critical Path Method (CPM) and a working-day calendar, then renders a Gantt chart you can open in a browser.

This README is for **people using the tool**. The companion `SKILL.md` is the playbook an AI agent follows when it edits schedules on your behalf — if you ask an agent to "add a task" or "build me a schedule," it reads `SKILL.md`.

## What the tool does (and doesn't)

- **You** write the schedule: what the work is, how long tasks take, what depends on what, and any fixed milestone dates.
- **The tool** computes start/finish dates, the critical path, and the project finish date, then renders a Gantt chart.
- The tool **never changes your YAML.** It only reads it and writes generated output into a `site/` folder. If something is wrong, it reports an error and you (or the agent) fix the YAML.

Out of scope: drag-and-drop Gantt editing, resource leveling, cost tracking, and cross-project links.

## Project layout

Everything for one schedule lives in a single folder:

```
my-project/
  schedule.yaml      # your schedule (any filename)
  calendar.yaml      # working days and holidays
  .gitignore         # added by the tool if absent — keeps site/ out of git
  recompute.sh       # added by the tool — recompute from this folder
  site/              # generated by the tool — never edit; safe to delete
    gantt.html
    ...
```

The tool writes a `.gitignore` (ignoring `site/`) into your project the first time you run `compute`. If you already have one, it is left untouched.

## The two files you write

### `schedule.yaml`

A list of `items`, each one a milestone, a task, or a group:

```yaml
title: Backyard Patio            # required; shown at the top of the Gantt page
calendar: calendar.yaml          # relative path to your calendar file
items:
  - kind: milestone              # a fixed date you set (e.g. a deadline or kickoff)
    id: 0
    name: Project start
    date: 2026-06-09

  - kind: group                  # a container that rolls up its children
    id: 10
    name: Permits
    predecessors: ["0FS"]
    children:
      - kind: task               # real work with a duration
        id: 11
        name: Submit application
        timing: auto
        duration: 1w
        predecessors: ["10SS"]
        percent_complete: 50      # required 0–100: draws a progress fill on the bar

  - kind: task
    id: 20
    name: Install pavers
    timing: auto
    duration: 4d
    predecessors: ["11FS"]
    percent_complete: 0
```

- **Milestone** — a zero-length point with a fixed `date` you choose. The only way to pin a date. The milestone at **`id: 0`** anchors the whole project; every schedule needs it.
- **Task** — work that takes time. Has a `duration` (e.g. `4d`, `2w`), `predecessors`, and a required `percent_complete: 0–100` (use `0` until work starts) that shows a progress fill on its bar (Microsoft Project style).
- **Group** — a heading that contains child items; its dates are derived from its children.

**Predecessors** say what must happen first, in Microsoft Project notation: `"11FS"` = start after item 11 finishes. Link types are `FS` (finish→start, the default), `SS`, `FF`, `SF`, with optional lag like `"11FS+3d"`. You usually just write `["0FS"]` for the first task and chain the rest.

The order of items in the file is the **top-to-bottom row order in the Gantt chart**, so arrange them to read as a timeline.

**People and events (optional)** — to graph context alongside the schedule, add `people` and/or `events` keys **above** `items`. **People** is staff availability (one band per person); **events** is calendar context not tied to a person (company events, holidays). Same shape; both are pure decoration and never affect scheduling:

```yaml
title: My Project
calendar: calendar.yaml
people:
  - name: Maria
    segments:
      - {start: 2026-06-15, finish: 2026-06-26, label: On vacation}
events:
  - name: Company
    segments:
      - {start: 2026-07-04, finish: 2026-07-04, label: Independence Day}
items:
  - ...
```

Segments can fall on any calendar day and must not overlap within a band. In the chart, people render on top and events below (two colors), with a single lock button to keep both pinned while scrolling.

Full field rules and examples: `design_docs/data_model.md`.

### `calendar.yaml`

Defines which days are working days. Durations and lag count working days only.

```yaml
weekends: [sat, sun]
holidays:
  - 2026-07-04
  - 2026-12-25
```

Both `weekends` and `holidays` are required (`holidays` may be an empty list). Milestone dates must land on a working day, or validation will tell you to move them.

## Running the tool

It's a [uv](https://docs.astral.sh/uv/) project. Install dependencies once:

```bash
cd skills/schedule
uv sync
```

**Validate** — check the schedule and calendar for problems without computing:

```bash
uv run validate <path-to-schedule.yaml>
```

**Compute** — validate, calculate all dates, render the Gantt, and serve it:

```bash
uv run compute <path-to-schedule.yaml>
```

`compute` prints the computed schedule and **two URLs** — a **local** one (`127.0.0.1`) for the machine running the tool and a **network** one for opening from another device on your network. Open whichever applies and the Gantt chart loads in your browser.

In the chart, click the ▸/▾ toggle on any group to collapse or expand its children; a collapsed group keeps its own summary bar. Use **Collapse all / Expand all** in the header to fold or unfold every group at once. **Show bar labels** in the header draws each item's name to the right of its bar (so you needn't read across to the left column); click again to hide them.

Useful flags:

- `--no-serve` — write the files but don't start the server (e.g. in CI).
- `--host 127.0.0.1` — serve on loopback only (don't expose on the network).
- `--port <n>` — use a different port (default `8000`).

## The edit → compute → refresh loop

The chart does **not** auto-update. Every time you change `schedule.yaml` or `calendar.yaml`:

1. Re-run `uv run compute <schedule.yaml>`.
2. **Refresh the browser tab** to see the new chart.

If you leave the server running, you can re-run `compute` in another terminal and just refresh.

A plain refresh (F5) always shows the fresh chart — the viewer fetches data with caching disabled and its scripts/styles are version-tagged each compute, so you never need a hard reload, an incognito window, or a cache wipe. This works no matter how `site/` is served; the built-in server also sends no-cache headers.

### Recompute without leaving the project folder

`compute` writes an executable `recompute.sh` into your project folder. It `cd`s into the installed skill, runs `compute --no-serve` on this schedule, and returns — so you can recompute from the project folder without typing the skill path:

```bash
./recompute.sh
```

It is regenerated on every `compute`, so it always points at the current skill install and schedule filename. It assumes the skill lives at `$HOME/.aschneer/skills/personal_skills/schedule`; edit that line if yours is elsewhere (the change is overwritten on the next `compute`).

## When validation fails

The tool reports **every** problem it finds at once, with a specific message per problem (e.g. a duplicate ID, a predecessor pointing at a task that doesn't exist, a milestone on a weekend, or a dependency cycle). Fix the YAML the messages point to and re-run. The tool will not guess or auto-fix — your file stays the source of truth.

## Optional: live validation while editing

To get inline schema errors as you type in VS Code / Cursor:

1. Install the [Red Hat YAML](https://marketplace.visualstudio.com/items?itemName=redhat.vscode-yaml) extension.
2. Copy `schemas/schedule.schema.yaml` and `schemas/calendar.schema.yaml` into your project.
3. Add a modeline as the **first line** of each file, pointing at the matching schema:

```yaml
# yaml-language-server: $schema=./schemas/schedule.schema.yaml
```

```yaml
# yaml-language-server: $schema=./schemas/calendar.schema.yaml
```

Adjust the relative path to wherever you put the schemas. The repo examples already include modelines.

## Working with an agent

You can ask an AI agent to drive the tool for you — for example:

- "Build a schedule from this list of tasks and durations."
- "Add a 2-week inspection task after the framing finishes."
- "The permit date slipped to the 22nd — update it and recompute."
- "Show me the Gantt chart."

The agent edits the YAML, runs `validate`/`compute`, shows you any errors and its planned fixes before changing files, and gives you the Gantt URL. What it does and the rules it follows are defined in `SKILL.md`.
